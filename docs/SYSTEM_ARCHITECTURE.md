# System Architecture

## 1. Runtime picture

```
Browser ──HTTPS──> Apache/LiteSpeed (public_html/.htaccess)
                      │  rewrites everything except /assets/* to index.php
                      ▼
                  index.php ──> app/bootstrap.php
                      │            ├─ Config  (config/config.php, generated by installer)
                      │            ├─ ErrorHandler (logs to storage/logs, generic page in prod)
                      │            ├─ Session (hardened cookie, DB-tracked sessions)
                      │            └─ Router  (web routes + /api/v1 routes)
                      ▼
          Middleware: SecurityHeaders → Installed? → Auth|ApiAuth → CSRF → RateLimit
                      ▼
                  Controller (thin: parse input, call service, choose view/JSON)
                      ▼
                  Services (business rules)   ── Events ──> Workflows, Webhooks, Notifications, Audit
                      ▼
                  RecordService (metadata engine: scope + tenant + validation)
                      ▼
                  DB (PDO, prepared statements, identifier whitelist)
                      ▼
                  MySQL 8 / MariaDB      Storage drivers: Local | S3 | Wasabi | S3-compatible | FTP | SFTP

cron.php (CLI or secret URL) ── jobs: email queue, webhook retries, scheduled workflows,
                                 recurring invoices, overdue marking, SLA breach, reminders, cleanup
```

## 2. Directory layout (everything lives in `public_html/`)

```
index.php            front controller
cron.php             scheduler entry
manifest.json        product + update metadata
.htaccess            rewrite, deny rules, headers
assets/              compiled CSS/JS, icons (public)
app/                 (denied) PHP source
  bootstrap.php
  Core/              framework: Router, Request, Response, DB, Schema, Session, Auth, Csrf,
                     Permissions, Validator, View, Crypto, Totp, RateLimiter, Mailer,
                     HttpClient (SSRF-safe), Events, Audit, Settings, Pdf, Xlsx, Updater
  Core/Storage/      StorageManager + LocalDriver, S3Driver, FtpDriver, SftpDriver
  Entities/          metadata definitions (one file per entity)
  Services/          RecordService, SalesService, ProjectService, TicketService,
                     WorkflowService, WebhookService, SearchService, ReportService, ...
  Http/Controllers/  web + API controllers
  Views/             PHP templates (layout, partials, pages)
  Database/          schema.php (single source of truth), seed.php, migrations/
config/              (denied) config.php — DB creds, app key
storage/             (denied) uploads, logs, cache, tmp, backups, sessions
vendor/              (denied) phpseclib, PHPMailer, Dompdf (+deps), autoload.php
install/             web installer assets (removed/locked after install)
docs/                these documents
```
Every PHP file under `app/`, `config/`, `vendor/` starts with a `defined('NX_ROOT') || exit;` guard as a second line of defence if `.htaccess` is ignored (e.g. Nginx without the shipped rules).

## 3. Metadata-driven record engine
Each entity is a PHP array in `app/Entities/<Name>.php`:
```php
return [
  'table' => 'leads', 'label' => 'Leads', 'singular' => 'Lead', 'module' => 'leads',
  'title' => 'name', 'icon' => 'target', 'board' => 'status', 'company_scoped' => true,
  'fields' => [
     'name'   => ['type' => 'text', 'required' => true, 'list' => true, 'search' => true],
     'status' => ['type' => 'select', 'options' => 'picklist:lead_status', 'filter' => true],
     'assigned_to' => ['type' => 'user', 'filter' => true],
     ...
  ],
  'related' => ['deals' => 'lead_id', 'tasks' => ['morph' => true]],
];
```
From this one definition the engine provides: list view (columns, sorting, filters, saved views, pagination), board view, detail page with inline edit, create/edit drawer, validation, CSV/XLSX export, CSV import mapping, REST endpoints, OpenAPI schema, global-search participation, permission checks, audit diffs, workflow field lists and custom fields.

Specialised behaviour (invoice totals, lead conversion, ticket threads, timers) lives in services that hook into the engine through events (`before_save`, `after_save`).

## 4. Request lifecycle details
- **Routing**: explicit route table (`app/routes.php`), patterns like `/r/{entity}/{id}`; entity names are validated against the metadata registry, never used directly in SQL.
- **Views**: server-rendered PHP templates with `e()` escaping; Alpine.js components add interactivity and call JSON endpoints under `/x/...` (session + CSRF header).
- **API**: `/api/v1/...` uses Bearer tokens (SHA-256 hashed at rest), its own rate limit bucket, JSON errors `{error:{code,message,fields}}`.

## 5. Multi-company / tenancy
- `companies` table; users get access to one or more companies (`company_user`).
- The active company is stored in the session and validated on every request.
- All business tables carry `company_id`; `RecordService` adds `company_id = :active` to **every** read and write and refuses cross-company relation IDs on save (relations are verified to exist inside the same company and the user's scope).

## 6. Events
`Events::dispatch('record.created', $entity, $record, $changes)` fans out synchronously to: Audit (diff), Notifications (assignment), Workflows (matching triggers; actions that call external URLs are queued), Webhooks (queued). Delivery happens on the next cron tick or immediately via a short shutdown function when cron is not configured.

## 7. File storage
`StorageManager::disk()` returns the active driver from settings. Each `files` row stores `driver` and `path`, so files keep resolving after the admin changes the default driver. Keys are generated server-side (`{company}/{yyyy}/{mm}/{random}.{ext}`) — user filenames never reach the storage path. Downloads stream through PHP with permission checks (or pre-signed S3 URLs valid 5 minutes when enabled).

## 8. Front-end
- Tailwind CSS 4 compiled at build time into `assets/css/app.css` (~60 KB gzip-friendly).
- Alpine.js 3 + a single `assets/js/app.js` holding components: command palette, toasts, confirm dialog, drawer form, data table, kanban (pointer-event drag that works on touch), inline editor, calendar, line-item editor, chart helpers.
- Theme: CSS variables + `.dark` class; light default, dark, or system.
- PWA `manifest.webmanifest` for add-to-home-screen.

## 9. Update mechanism
`manifest.json` holds `update.server`. The updater fetches `{server}/latest.json` → `{version, url, sha256, signature}`; verifies the Ed25519 signature over `version|sha256` with the public key in `manifest.json`; downloads through the SSRF-safe client; checks SHA-256; backs up DB (SQL dump) and app files to `storage/backups`; extracts while preserving `config/` and `storage/`; runs pending migrations; writes the new version. Maintenance mode is on during the update.

## Extension registry (v2.0)

`App\Core\Extensions` lets features plug into the application without editing core files. `Extensions::boot()` runs on every web request and in `cron.php`: it loads `app/features.php` (the built-in v2 features) and then every enabled module from `modules/<slug>/module.php`.

| Hook | Consumed by |
|---|---|
| `nav()` | `EntityRegistry::nav()` → sidebar groups (permission-filtered) |
| `routes()` | `App::run()` after `app/routes.php` (first match wins, so core routes take precedence) |
| `panel()` | `records/show.php` — main column (before tabs) and sidebar cards |
| `cron()` | `CronService::run()`; `perCompany` jobs run inside `Auth::actingAs()` for each active company |
| `settingsTab()` | `partials/settings_nav.php` |
| `permission()` | `Permissions::extraModules()` → role editor |
| `workflowAction()` | `WorkflowService::actions()` / `runAction()` |
| `entityDir()`, `viewDir()` | `EntityRegistry::all()`, `View::partial()` |

`Auth::actingAs($userId, $companyId, fn)` is used wherever there is no signed-in staff user — public documents, the client portal, payment webhooks and cron — so that settings, numbering and tenant filters resolve for the right company.

Public, unauthenticated entry points added in 2.0: `/portal/*` (own session), `/p/{type}/{token}` (documents, signing, payment), `/hooks/pay/{gateway}/{company}` (signed webhooks), `/pay/return/…`, `/help`, `/unsubscribe/{token}`. Each validates its own token or signature; none trusts IDs from the request without it.
